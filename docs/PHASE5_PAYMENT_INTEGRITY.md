## 2. x402 v2 Protocol & Wire Format Alignment

### Supported HTTP Headers & Aliases
The seller and buyer adapters strictly adhere to x402 v2 specifications while supporting backwards-compatible aliases:

| Header Name | Role | Originator | Status Code |
|-------------|------|------------|-------------|
| `X-402-Requirement` | Emits payment requirements (CAIP-2 network, token, recipient, atomic amount, nonce) | Seller | 402 Payment Required |
| `PAYMENT-REQUIRED` | x402 v2 standard alias for payment requirement | Seller | 402 Payment Required |
| `X-402-Payment-Payload` | Submits signed payment authorization payload | Buyer | Retried Request (POST) |
| `PAYMENT-SIGNATURE` | x402 v2 standard alias for signed payload | Buyer | Retried Request (POST) |
| `X-402-Settlement-Proof` | Returns verified transaction hash or facilitator receipt identifier | Seller | 200 OK |
| `PAYMENT-RESPONSE` | x402 v2 standard alias for settlement evidence | Seller | 200 OK |

### Requirement Challenge Validation
Challenges generated by `SellerPaymentVerifier.issue_challenge()` and `backend/sellers/routes.py` require:
1. `version`: `"2.0"`
2. `network`: `"eip155:84532"` (Base Sepolia CAIP-2)
3. `token`: `"0x036CbD53842c5426634e7929541eC2318f3dCF7e"` (Base Sepolia USDC)
4. `amount`: Integer string of USDC base units (`1 USDC = 1,000,000 units`)
5. `payTo`: Authoritative recipient address of the seller
6. `nonce`: Cryptographically unique nonce (`nonce_<uuid.hex>`)
7. `service_id`: Catalog identifier of the invoked service

## 3. Buyer Pre-Payment Verification (Policy Enforcement)

Before signing any payment challenge, `PaymentPolicyVerifier.verify()` in `backend/payments/policy.py` validates:
- **Registered Price Protection:** The challenged price cannot exceed the registered catalog price (`price_gouging` check).
- **Network Confinement:** Must strictly match `eip155:84532`. Any foreign chain ID is immediately rejected.
- **Token Confinement:** Must strictly match Base Sepolia USDC. Unknown tokens are rejected.
- **Recipient Verification:** The `payTo` address must exactly match the registered seller address in `service_catalog`.
- **Budget Lock:** The buyer locks the exact required base units with `BudgetManager.reserve()` *before* invoking the seller with payment.

## 4. Seller Verification & Execution Boundaries

Seller endpoints (`backend/sellers/routes.py`) enforce the following sequence:
1. **Initial Call (No Payment):** Request body received without `X-402-Payment-Payload`. Seller halts execution immediately and responds with HTTP 402 and `X-402-Requirement`. **Zero seller business logic executes.**
2. **Re-Request with Payload:**
   - Seller parses `X-402-Payment-Payload`.
   - If payload is malformed or invalid JSON: Returns HTTP 402 with fresh challenge.
   - Seller invokes `seller_payment_verifier.verify_and_settle(payload, requirement)`.
   - In live mode (`test_mode=False`), if signature is synthetic (`0x_mock_...`), verification fails with `SettlementVerificationError` and returns HTTP 402.
   - Only upon verified payment does the seller invoke the provider (`execute_provider`).
3. **Delivery:**
   - Upon provider completion, seller returns HTTP 200 with result and header `X-402-Settlement-Proof: rec_auth_<id>` or `<tx_hash>`.

## 5. Settlement Verification Engine (6-Point On-Chain Validation)

In `SettlementVerifier.verify_full_settlement()`:
1. **Network Check:** Rejects any `expected_network != "eip155:84532"`.
2. **Receipt Status:** Queries Base Sepolia JSON-RPC via `eth_getTransactionReceipt`. Confirms `status == 0x1`. Status `0x0` raises `SettlementVerificationError("unconfirmed or reverted")`.
3. **Target Token Contract:** Validates log address equals `USDC_BASE_SEPOLIA`.
4. **Verified Seller Recipient:** Validates topic[2] matches seller `payTo` address.
5. **Exact Integer Amount:** Validates log `data` field integer base units match `expected_amount_units`.
6. **Decoded ERC-20 Transfer Log:** Validates topic[0] equals `0xddf252ad1be2c89b69c2b068fc378daa952ba7f163c4a11628f55a4df523b3ef`.

### Fail-Closed Behavior
- If JSON-RPC is unreachable or returns HTTP error: In live mode, fails closed.
- If receipt contains no logs matching the transfer: Fails closed with `SettlementVerificationError`.
- If facilitator URL is not configured or returns non-200 / non-confirmed status: Fails closed.
