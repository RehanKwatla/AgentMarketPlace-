## 1. Purpose

This document defines the technology stack and repeatable development environment for the DI-06 solution. All four team members should use this document as the common reference for installing tools, configuring local services, managing environment variables, running the application, testing payment flows, and preparing deployment.

The implementation is a **modular monolith** for the hackathon: one repository and a coordinated backend application, with distinct registry, buyer, payment, ledger, reputation, and seller modules. The Data, Scraping, and Inference sellers must remain independently addressable service endpoints and must each implement the required x402 v2 behavior. They may share a codebase and deployment initially; do not make the architecture unnecessarily complex with microservices or Kubernetes.

### 1.1 Core implementation rule

Build the mandatory requirements first:

1. Searchable service registry.
2. Three paid sellers: Data, Scraping, and Inference.
3. Natural-language buyer agent with a budget.
4. Real testnet stablecoin settlement through x402 v2.
5. Durable ledger and transaction evidence.
6. Deterministic spending, price, recipient, network, and token checks.
7. Durable replay protection and concurrency-safe budget reservations.
8. Output validation, fallback, and seller reputation.
9. Interoperability with unmodified x402 v2 implementations.
10. Public demonstration endpoints, setup instructions, and reproducible tests.

Do not implement escrow, a second chain, MCP/A2A payments, complex agent chaining, or other stretch goals until the mandatory flow and its safety tests pass.

### 2.1 Important SDK decision gate

1. Open the official x402 documentation and repository.
2. Select the official x402 **v2** client and server integrations that fit the chosen backend runtime.
3. Confirm the SDK supports the required Base Sepolia network and the configured USDC asset.
4. Confirm the facilitator URL and required facilitator behavior.
5. Build a minimal seller endpoint that returns `402 Payment Required` to an unpaid request.
6. Use a compatible client to complete one real testnet paid request.
7. Record the exact package names and versions in the repository's dependency lockfiles and in the implementation notes.
8. Do not hand-roll protocol headers or settlement behavior when the official SDK already provides it.

If the team's selected official integration requires TypeScript/Node for a particular x402 role, use a small, clearly bounded adapter service for that role rather than inventing a nonstandard flow. Keep the external interface documented and interoperable. The application must still pass tests against unmodified x402 v2 clients and sellers.

```text

  |
  +--------------------+
  |                    |

                       |
                       v
                  Testnet USDC
```

The diagram is conceptual. Follow the selected official SDK's actual payment lifecycle and responsibility boundaries. Do not assume that the buyer directly performs every verification or settlement action; this depends on the protocol flow and selected integration.

### 3.1 Deterministic payment policy

The language model may help translate a user's request into a plan, select among eligible services, and explain results. It must not authorize or override payment policy.

Before authorizing a paid call, deterministic code must validate at least:

- The service exists in the trusted registry.
- The payment request corresponds to the expected service.
- The requested price does not exceed the approved registry price.
- The token/asset and network match the approved configuration.
- The pay-to address matches the approved registry record.
- The budget has enough unreserved funds.
- The request is not a replay of an already-consumed authorization.
- The request is within the configured concurrency limit.
- The request and response schemas are valid.

Use integer USDC base units for internal arithmetic. Do not use binary floating-point values for payment authorization or budget accounting.

### 3.2 Seller endpoints

The required categories are:

- **Data Seller:** returns structured data from a local dataset, public API, or defined source.
- **Scraping Seller:** retrieves permitted public information and returns normalized structured results.
- **Inference Seller:** performs an inference, classification, extraction, or summarization operation.

Each seller must have its own registry record and independently callable URL/path. Each seller must use the selected x402 v2 server integration and must return the protocol's payment challenge when an unpaid request requires payment.

### 3.3 Persistent data

PostgreSQL should persist:

- Service registry entries.
- Tasks and task execution status.
- Individual service-call attempts.
- Budget reservations and releases.
- Payment authorization/idempotency identifiers, where appropriate and safe.
- Settlement evidence and transaction hashes.
- Output-validation outcomes.
- Seller reputation aggregates.
- Timestamps, latency, and error reasons.

Do not store private keys in the database. Do not store unnecessary raw payment credentials or authorization material in logs.

## 11. x402 v2 Integration Setup

This section defines the expected setup sequence, not a replacement for the official SDK documentation.

### 11.1 Seller-side setup

For each seller:

1. Register its endpoint and payment configuration.
2. Configure the expected network and supported USDC asset.
3. Configure the receiving `payTo` address.
4. Use the official x402 v2 server integration appropriate for the runtime.
5. Make an unpaid request and confirm it receives a valid `402 Payment Required` challenge.
6. Make a valid paid request using a compatible x402 client.
7. Verify the payment using the documented flow.
8. Confirm settlement evidence before treating the request as paid.
9. Release the protected result only according to the protocol lifecycle.
10. Record the call outcome and latency.

The seller must not trust a client-provided claim that payment has occurred. Follow the SDK's verification and settlement responsibilities.

### 11.2 Buyer-side setup

1. Query the registry to discover services.
2. Select a service only after checking the task requirements and reputation.
3. Retrieve the seller's payment challenge using the supported x402 flow.
4. Compare the requested price, asset, network, and `payTo` address against the trusted registry record.
5. Reserve budget atomically before authorizing spending.
6. Enforce request identity and replay/idempotency rules.
7. Authorize and send payment through the official x402 client.
8. Validate the seller's output against its declared schema.
9. Reconcile settlement evidence.
10. Persist the final status and release or finalize the budget reservation according to the verified payment outcome.

### 11.3 Do not assume failures are unpaid

A timeout may happen before payment, during verification, or after a transaction has been broadcast. These cases are not equivalent.

Use distinct outcomes such as:

- `paid`
- `paid_output_rejected`
- `refused`
- `failed_and_not_charged`
- `pending_reconciliation` (internal transient state, if needed)

Only use `failed_and_not_charged` when the implementation has enough evidence to support that conclusion. For uncertain settlement, reconcile before retrying.

### 11.4 Interoperability

The team must test both directions:

- An unmodified reference x402 v2 client pays one of the team's sellers.
- The team's buyer calls and pays an unmodified reference x402 v2 seller.

Passing a test against only the team's own client and server is not enough to demonstrate interoperability.

### 13.3 Logging policy


Run the project's test/lint scripts if they are configured in `package.json`.

### 15.3 Required payment tests

Test at least:

1. Unpaid seller request returns the expected x402 v2 payment challenge.
2. Valid payment completes a real testnet paid call.
3. Actual settlement evidence and transaction hash are recorded.
4. Requested price above registry price is refused.
5. Incorrect `payTo`, token, or network is refused.
6. Budget is never exceeded at concurrency 1 and concurrency 5.
7. Configured maximum concurrency supports at least 3 concurrent calls.
8. Replaying the same authorization serially does not unlock a second response.
9. Replaying the same authorization in parallel does not unlock multiple responses or cause duplicate settlement.
10. Seller failure before settlement does not cause settlement.
11. Invalid seller output is rejected and reputation is lowered.
12. Fallback is attempted only when the remaining budget allows it.
13. The ledger reconciles with on-chain transfer evidence.
14. External x402 v2 client-to-team-seller interoperability works.
15. Team-buyer-to-reference-seller interoperability works.
16. Secret scan passes.

### 15.4 Test data

Use synthetic, non-sensitive test data. Do not seed fake transaction hashes or make local mock payments appear as real settlement. If using mocks in unit tests, clearly label them as mocked and keep separate tests that verify the actual testnet flow.

## 18. Suggested Implementation Order

Follow this order to reduce integration risk.

### Phase 1 — Environment and contract freeze
- Create the repository and branches.
- Agree on dependency and runtime versions.
- Create `.env.example` and `.gitignore`.
- Define service, task, seller output, ledger, and error schemas.
- Start PostgreSQL and the basic FastAPI/React applications.

### Phase 2 — One real x402 paid call
- Implement one minimal seller.
- Configure Base Sepolia and the supported testnet USDC asset.
- Configure the official x402 v2 SDK.
- Verify the unpaid `402` response.
- Complete a valid paid request.
- Record the transaction hash and verify it on the explorer.

### Phase 3 — Core services
- Add the other two sellers.
- Implement the service registry.
- Implement buyer service discovery and task execution.
- Validate outputs against the declared schemas.

### Phase 4 — Safety and ledger
- Implement atomic budget reservations.
- Implement registry price/token/network/recipient checks.
- Implement durable replay protection.
- Persist every attempted call.
- Reconcile uncertain settlements.
- Implement reputation and affordable fallback.
- Run adversarial tests.

### Phase 5 — Dashboard and deployment
- Complete task submission, marketplace, results, ledger, and reputation screens.
- Deploy public HTTPS endpoints.
- Run the three-category demo tasks.
- Run interoperability tests.
- Perform the secret scan and prepare the five-minute demonstration.
